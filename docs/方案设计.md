## 技术方案概述

为 skynamecat 网站新增一个独立后台：现有 Next.js 继续静态导出，由 Nginx 提供页面和庞菠菠资源；新增 FastAPI 服务负责对话 API、预制问答匹配、会话记录和管理界面；现有 PostgreSQL 保存对话配置和历史。后台运行在 Docker 中，仅监听服务器本机，由 Nginx 将同域的 `/api/` 和 `/admin/` 转发给后台。

第一阶段不接入真实大模型，使用可管理的“规则模型”：把访客问题标准化后，按精确词、关键词和正则规则计算命中分数，从多个预制回答中按权重选取一个。规则模型与真实模型都实现统一的 `ChatProvider` 接口；将来只需新增真实模型 Provider，并在低置信度时调用它，不必重写前端、会话表或管理后台。

## 需求与约束

- 当前前端为 Next.js 16，使用 `output: "export"`，线上是纯静态文件，不能直接承载服务端 API。
- 服务器已有 Nginx、Docker 和 PostgreSQL 18；系统 Python 3.6 过旧且没有 Node，因此后台运行时放入 Docker。
- PostgreSQL 仅监听 `127.0.0.1:5432`，继续保持不对公网开放。
- 第一阶段需要预制对话和一个可编辑规则的后台，表现得像一个简单模型。
- 后续需要能平滑接入真实模型、流式输出和知识库。

## 技术选型

| 类别 | 选择 | 理由 |
|------|------|------|
| 网站前端 | 保留现有 Next.js 静态导出 | 不破坏现有页面、动画和部署方式 |
| 后台 API | Python 3.12 + FastAPI | API 简洁，后续接 AI、向量检索和文本处理方便 |
| 管理界面 | FastAPI 模板 + HTMX | 单管理员场景足够轻，无需再维护一套管理端前端工程 |
| ORM / 迁移 | SQLAlchemy 2 + Alembic | PostgreSQL 支持成熟，数据库变更可追踪 |
| 数据库 | 现有 PostgreSQL 18 | 已安装且仅本机监听，不增加新存储系统 |
| 运行方式 | Docker Compose + host network | 隔离新运行时，同时能访问只监听本机的 PostgreSQL |
| 入口与 TLS | Nginx 同域反向代理 | 浏览器只访问 HTTPS 同源 `/api`，避免跨域和混合内容问题 |

## 假模型工作方式

1. 去除多余空格、统一大小写和常见标点。
2. 依次匹配 `exact`、`contains`、`regex` 三类规则。
3. 按规则权重、意图优先级和匹配长度计算分数。
4. 达到阈值时，从该意图启用的回答中按权重选取。
5. 未达到阈值时返回自然的兜底回答，并把未命中问题记录到后台，方便继续补规则。
6. 返回 `provider`、`intent`、`confidence` 等内部信息，但前端只显示回答文本。

首批预制意图建议包括：问候、自我介绍、作品/项目、网站内容、技术方向、联系方式、庞菠菠、音乐、网站模式、告别和兜底。每个意图准备 3～5 种回答，避免每次回复完全相同。

# 庞菠菠盲盒管理与动作质量升级方案

## 技术方案概述

现阶段不进行整个管理后台的前后端分离重写，而采用“Spring Boot 统一后端 + 现有 Thymeleaf 管理页 + 盲盒管理局部 SPA”的渐进式架构。

现有对话规则、未命中问题、请求记录等页面继续使用 Thymeleaf，避免为已经稳定的 CRUD 页面增加构建与部署复杂度；新增的盲盒配置、3D 模型预览、动画时间轴、概率模拟、素材上传和发布回滚使用 React + Three.js 构建独立管理模块，挂载在 `/manage/blindbox/`。模块与 Spring Boot 同源部署，继续使用现有 Session 与 CSRF，不额外引入 JWT。

动作质量方面，不再把当前脚本生成的稀疏骨骼旋转直接当成正式动画。建立统一骨架、标准动作源、IK 足底锁定、道具约束、动画分层、淡入淡出和自动验收的完整管线。先打磨 Idle、Walk、Groove 三个标杆动作，通过后再扩展全部动作，避免一次制作二十多个动作后整体返工。

## 架构方案比较

| 方案 | 说明 | 3D 管理能力 | 改造风险 | 结论 |
|------|------|------------|----------|------|
| 保持纯 Thymeleaf | 所有新页面继续服务端渲染 | 时间轴、持续画布状态、局部高频调参实现困难 | 低，但后续维护成本高 | 不推荐用于 3D 管理 |
| 整个后台改为独立 SPA | 登录、对话、日志、盲盒全部重写 | 强 | 高，需要重做成熟页面与权限链路 | 暂不采用 |
| 局部 SPA | 现有后台保留，盲盒管理独立 React 页面 | 强 | 中低，可分阶段交付 | 推荐 |

## 技术选型

| 类别 | 选择 | 理由 |
|------|------|------|
| 后端 | Spring Boot MVC | 延续现有后端、Security、JPA、Flyway 与请求追踪体系 |
| 现有管理页 | Thymeleaf | 对话、日志等 CRUD 页面稳定，暂无重写收益 |
| 盲盒管理页 | React + TypeScript + Vite | 适合 Three.js 画布、复杂表单、时间轴和持续前端状态；可独立构建后嵌入后台 |
| 3D 运行时 | Three.js | 当前盲盒已经使用，迁移成本最低 |
| 数据库 | PostgreSQL | 保存系列、角色、权重、动画元数据和发布版本 |
| 二进制素材 | 文件系统或对象存储 | GLB 不进入数据库；数据库只存 URL、Hash、大小、版本和状态 |
| 动画制作 | Blender | 统一骨架、约束、NLA、烘焙和 glTF 导出 |
| 鉴权 | Spring Security Session + CSRF | 管理页和 API 同源，无需 JWT 和额外刷新令牌体系 |

## 动作质量升级方案

### 当前问题判断

当前动作主要由脚本给少量骨骼写入欧拉旋转关键帧，缺少重心、足底接触、关节约束、身体反向运动和动作过渡。因此“能动”但容易出现脚滑、身体漂浮、手脚不同步、动作突然切换和道具穿模。该方式可保留为动作原型工具，不适合作为最终成片标准。

### 1. 骨架基线

- 选定唯一权威模型和 `skeleton-v1`，统一比例、Rest Pose、骨骼轴向和命名。
- 在 Blender 中应用模型变换，清理重复骨架和无效动作。
- 以后所有动作都对同一骨架制作或重定向；不兼容骨架禁止直接发布。

### 2. 三个标杆动作

先只完成并验收：

1. `Idle`：呼吸、轻微重心变化、眨眼/看向，首尾无跳变。
2. `Walk`：原地循环、足底锁定、骨盆上下与左右移、手臂反向摆动。
3. `Groove`：验证髋、胸、肩、头的节奏传递和夸张程度。

三个动作风格确认后，再批量扩展手机、电脑、喝奶茶、吃蛋糕以及其他舞蹈动作。

### 3. Blender 制作规范

- 腿部使用 IK 和足底控制器，落地帧锁定脚掌，消除脚滑。
- 道具使用 `Child Of`、IK 或 Copy Transform 约束，保证手掌与手机、电脑、杯子、蛋糕接触稳定。
- 头部和眼睛建立目标点：玩手机看屏幕、看电脑看屏幕中心、喝饮料看杯口。
- 动作分为主运动与次级运动：先处理重心和四肢，再加入头发、衣物、呼吸和轻微延迟。
- 每个片段进入独立 NLA Track，最终只烘焙变形骨骼后导出。
- 统一 30 FPS；循环动作首尾连续，导出时避免重复最后一帧造成停顿。
- 模型在动画文件中保持原地，网页中的水平移动由运行时控制，避免 Root Motion 与网页位移叠加。

### 4. 运行时动作系统

```text
基础层：Idle / Walk / Rest / Dance
上半身叠加层：Listen / Phone / Wave / Drink
道具层：Headphones / Phone / Laptop / Cup / Cake
状态机：enter -> loop -> exit
```

- 使用 `AnimationMixer` 的淡入淡出，普通切换建议 0.25–0.45 秒，禁止瞬间停掉旧动作再启动新动作。
- “听歌”是可叠加状态：耳机绑定头骨，音乐符号独立；可以与 Walk、Idle、Groove 并存。
- “玩手机/喝奶茶”等涉及双手和道具的动作，第一阶段作为互斥基础动作，避免骨骼层冲突。
- 对可叠加动作使用上半身遮罩或独立动画层；不要简单同时播放两个全身 Clip。
- 限制异常大的帧间隔，页面从后台恢复时不让角色突然跳步。
- 公开端只根据状态机切换动作，不直接散落调用 `clipAction().play()`。

### 5. 导出与加载

- 保留一个权威 `.blend` 源文件，生成物禁止反向作为下一轮编辑源。
- 生成 `lite`、`balanced`、`full` 三档，默认先加载 `lite`。
- 首屏只加载模型和当前必要动作，其余舞蹈包按需加载。
- 在兼容性验证后再引入 Meshopt/Draco 与 KTX2；压缩不能以骨骼动画失真为代价。
- 每个版本同时输出 manifest：模型 Hash、骨架版本、Clip 名称、时长、循环方式和文件大小。

## 动作验收门槛

| 项目 | 验收标准 |
|------|----------|
| 循环 | 首尾肉眼无跳帧、无明显停顿 |
| 脚步 | 支撑脚落地阶段不滑动、不漂浮 |
| 重心 | 骨盆移动与支撑腿一致，不像平移木偶 |
| 协调 | 手臂与腿反向摆动，肩、胸、髋存在合理传递 |
| 道具 | 手掌不脱离道具，手机/杯子不穿身体 |
| 注视 | 手机、电脑、饮料动作都有明确视线目标 |
| 过渡 | 0.25–0.45 秒内自然切换，无瞬移或姿势弹回 |
| 性能 | 桌面目标 60 FPS，主流移动设备不低于 30 FPS |
| 兼容 | Chrome、Edge、移动 Safari 基本行为一致 |

## 关键设计决策

| 决策点 | 选择 | 理由 |
|--------|------|------|
| 是否整个后台前后端分离 | 否，先做盲盒局部 SPA | 复杂交互得到 SPA 能力，又不重写稳定页面 |
| 是否独立域名部署管理端 | 否，同源部署 | 复用 Session/CSRF，避免 CORS 和双重登录 |
| 是否把 GLB 存数据库 | 否 | 数据库膨胀、备份和缓存效率差 |
| 是否一次重做全部动作 | 否，先做 3 个标杆动作 | 先锁定骨架、节奏和质量标准，降低批量返工 |
| 是否沿用脚本自动生成动作 | 只用于原型 | 稀疏旋转无法替代重心、接触和约束打磨 |
| 网页位移方式 | 动画原地循环，JS 控制位置 | 避免 Root Motion 方向、速度和边界难以统一 |
| 听歌是否互斥 | 不互斥，作为叠加状态 | 满足边走边听，同时保持耳机绑定头部 |

## 风险与待确认项

1. 动作质量主要受源骨架和人工动画投入影响，单靠前端代码无法把低质量 Clip 自动变自然。
2. 若当前 FBX/GLB 没有完整权重或骨骼结构异常，需要先在 Blender 修骨架，阶段 3 工期会增加。
3. Git 仓库不适合持续累积大型二进制源文件；应在阶段 0 确认 Git LFS 或外部素材存储。
4. 用户确认三个标杆动作的风格后，才进入批量制作，以该确认点作为里程碑。

## Provider 接口

```java
public interface ChatProvider {
    ChatResult reply(ChatContext context, String message);
    String name();
}
```

- `PresetChatProvider`：从 PostgreSQL 加载启用规则，完成关键词/正则评分和预制回答选择。
- `SpringAiProvider`：以后通过 Spring AI 的 `ChatClient` 调用真实模型。
- `RoutingChatProvider`：未来可先跑预制规则，低于置信度阈值时再转真实模型。

这种结构保证前端始终调用同一个 `/api/v1/chat`，切换模型不影响页面。

## 关键调整

| 决策点 | 选择 | 理由 |
|--------|------|------|
| Spring Boot 还是 FastAPI | Spring Boot | 用户明确偏好，长期后台、权限、数据管理和 AI 扩展更体系化 |
| Spring WebFlux 还是 MVC | MVC | 第一阶段均为短请求；无需为假模型提前引入响应式复杂度 |
