## 技术方案概述

为 skynamecat 网站新增一个独立后台：现有 Next.js 继续静态导出，由 Nginx 提供页面和庞菠菠资源；新增 FastAPI 服务负责对话 API、预制问答匹配、会话记录和管理界面；现有 PostgreSQL 保存对话配置和历史。后台运行在 Docker 中，仅监听服务器本机，由 Nginx 将同域的 `/api/` 和 `/admin/` 转发给后台。

第一阶段不接入真实大模型，使用可管理的“规则模型”：把访客问题标准化后，按精确词、关键词和正则规则计算命中分数，从多个预制回答中按权重选取一个。规则模型与真实模型都实现统一的 `ChatProvider` 接口；将来只需新增真实模型 Provider，并在低置信度时调用它，不必重写前端、会话表或管理后台。

## 需求与约束

- 当前前端为 Next.js 16，使用 `output: "export"`，线上是纯静态文件，不能直接承载服务端 API。
- 服务器已有 Nginx、Docker 和 PostgreSQL 18；系统 Python 3.6 过旧且没有 Node，因此后台运行时放入 Docker。
- PostgreSQL 仅监听 `127.0.0.1:5432`，继续保持不对公网开放。
- 第一阶段需要预制对话和一个可编辑规则的后台，表现得像一个简单模型。
- 后续需要能平滑接入真实模型、流式输出和知识库。

## 技术选型

| 类别 | 选择 | 理由 |
|------|------|------|
| 网站前端 | 保留现有 Next.js 静态导出 | 不破坏现有页面、动画和部署方式 |
| 后台 API | Python 3.12 + FastAPI | API 简洁，后续接 AI、向量检索和文本处理方便 |
| 管理界面 | FastAPI 模板 + HTMX | 单管理员场景足够轻，无需再维护一套管理端前端工程 |
| ORM / 迁移 | SQLAlchemy 2 + Alembic | PostgreSQL 支持成熟，数据库变更可追踪 |
| 数据库 | 现有 PostgreSQL 18 | 已安装且仅本机监听，不增加新存储系统 |
| 运行方式 | Docker Compose + host network | 隔离新运行时，同时能访问只监听本机的 PostgreSQL |
| 入口与 TLS | Nginx 同域反向代理 | 浏览器只访问 HTTPS 同源 `/api`，避免跨域和混合内容问题 |

## 架构设计

```text
浏览器
  └─ HTTPS / 同一个域名
      └─ Nginx
          ├─ /              -> /www/wwwroot/testProject（静态网站）
          ├─ /api/v1/*      -> 127.0.0.1:8000（FastAPI）
          └─ /admin/*       -> 127.0.0.1:8000（管理后台）
                                 ├─ RuleChatProvider（第一阶段）
                                 ├─ LlmChatProvider（以后启用）
                                 └─ PostgreSQL 127.0.0.1:5432
```

后台内部采用四层：

1. 路由层：校验请求、鉴权、返回稳定的 API 格式。
2. 对话服务层：维护会话、调用 Provider、记录消息。
3. Provider 层：规则模型和未来真实模型使用相同接口。
4. 数据层：SQLAlchemy 仓储和 PostgreSQL。

## 模块划分

| 模块 | 职责 | 依赖 |
|------|------|------|
| `chat_api` | 接收问题并返回回答 | `chat_service` |
| `chat_service` | 会话编排、记录消息、选择 Provider | `providers`、`repositories` |
| `rule_provider` | 文本标准化、规则打分、回答选择、兜底 | 对话规则仓储 |
| `llm_provider` | 后续封装真实模型调用 | 模型供应商 API |
| `admin` | 登录、对话意图/触发词/回答的增删改查 | 对话规则仓储 |
| `repositories` | 封装 PostgreSQL 查询 | SQLAlchemy |
| `seed` | 初始化第一批预制对话 | Alembic / 数据库 |

## 假模型工作方式

1. 去除多余空格、统一大小写和常见标点。
2. 依次匹配 `exact`、`contains`、`regex` 三类规则。
3. 按规则权重、意图优先级和匹配长度计算分数。
4. 达到阈值时，从该意图启用的回答中按权重选取。
5. 未达到阈值时返回自然的兜底回答，并把未命中问题记录到后台，方便继续补规则。
6. 返回 `provider`、`intent`、`confidence` 等内部信息，但前端只显示回答文本。

首批预制意图建议包括：问候、自我介绍、作品/项目、网站内容、技术方向、联系方式、庞菠菠、音乐、网站模式、告别和兜底。每个意图准备 3～5 种回答，避免每次回复完全相同。

## 接口设计

### 对话接口

- 请求方式：`POST`
- 路径：`/api/v1/chat`
- 请求体：

```json
{
  "session_id": "可选 UUID",
  "message": "你最近在做什么？"
}
```

- 响应：

```json
{
  "code": 0,
  "data": {
    "session_id": "UUID",
    "message_id": "UUID",
    "answer": "最近在打磨这个小站，也在照顾庞菠菠。",
    "provider": "preset",
    "intent": "current_work",
    "confidence": 0.92
  }
}
```

### 健康检查

- 请求方式：`GET`
- 路径：`/api/healthz`
- 用途：Nginx、发布脚本和故障排查确认后台及数据库状态。

### 管理后台接口

- `POST /admin/login`：单管理员登录。
- `GET /admin/intents`：查看意图及启用状态。
- `POST /admin/intents`：新建意图。
- `POST /admin/intents/{id}`：编辑优先级、触发规则和回答。
- `POST /admin/intents/{id}/toggle`：启停意图。
- `GET /admin/unmatched`：查看未命中的访客问题。

## 数据模型

### `dialog_intents`

- `id` UUID 主键
- `key` 唯一稳定标识，例如 `greeting`
- `name` 后台显示名称
- `priority` 优先级
- `enabled` 是否启用
- `created_at`、`updated_at`

### `dialog_patterns`

- `id` UUID 主键
- `intent_id` 外键
- `match_type`：`exact` / `contains` / `regex`
- `pattern` 匹配内容
- `weight` 权重
- `enabled` 是否启用

索引：`intent_id`、`enabled`。

### `dialog_replies`

- `id` UUID 主键
- `intent_id` 外键
- `content` 回答文本
- `weight` 随机选择权重
- `enabled` 是否启用

### `chat_sessions`

- `id` UUID 主键
- `visitor_id` 匿名访客标识，可为空
- `created_at`、`last_active_at`

### `chat_messages`

- `id` UUID 主键
- `session_id` 外键
- `role`：`visitor` / `assistant`
- `content` 消息内容
- `provider`：`preset` / `llm`
- `intent_id` 可空外键
- `confidence` 可空
- `created_at`

索引：`session_id, created_at`、`intent_id`。

## 安全设计

- 数据库继续仅监听本机，不开放公网端口。
- 数据库密码、管理后台密钥和未来模型 API Key 写入服务器专用环境文件，不进入项目或 Git；文件权限设为仅 root 可读。
- 管理后台使用 Argon2 密码哈希和 `HttpOnly + Secure + SameSite=Strict` 会话 Cookie。
- API 与网站同源，默认不开放宽泛 CORS。
- 对话接口限制正文长度并按 IP 哈希限流；不保存原始 IP。
- 所有数据库操作参数化；正则规则设置长度限制和执行保护。

## 关键设计决策

| 决策点 | 选择 | 理由 |
|--------|------|------|
| 是否改成动态 Next.js | 暂不改 | 现有静态站稳定，后台独立后边界更清楚 |
| 假模型放前端还是后台 | 放后台 | 对话可在线编辑、可记录未命中问题，也能无缝换真实模型 |
| 是否现在接真实模型 | 暂不接 | 先验证对话体验和内容，控制成本与复杂度 |
| 是否现在做流式输出 | 第一阶段返回完整 JSON | 预制回答很快；接口保留 Provider 层，接真实模型时再增加流式端点 |
| 后台管理技术 | 服务端模板 + HTMX | 单管理员、少量表单场景更轻、更安全、更容易部署 |
| 是否使用现有 D1 代码 | 不使用 | 当前线上服务器已有 PostgreSQL；项目里的 D1 只是未启用的模板代码 |

## 实现计划

1. 建立 `backend/`：FastAPI、Docker Compose、环境配置模板、健康检查。
2. 建立 PostgreSQL 表、Alembic 迁移和首批预制对话种子。

7. 验证桌面端/移动端对话、后台权限、数据库记录与断线恢复。

## 后续演进

- 新增 `LlmChatProvider`：规则置信度低时再调用真实模型。

## Spring Boot 方案调整

后台技术栈由 FastAPI 调整为 Spring Boot。整体部署边界、接口和 PostgreSQL 数据模型保持不变，现有静态 Next.js 网站仍由 Nginx 提供，Spring Boot 独立承载 `/api/` 与 `/admin/`。

## 技术选型

| 类别 | 选择 | 理由 |
|------|------|------|
| Java | Eclipse Temurin 21 LTS | 成熟稳定，运行在 Docker 内，不依赖服务器本机 Java |
| 后台框架 | Spring Boot 4.1 | 新项目直接使用当前稳定主线，并可接 Spring AI 2.0 |
| Web | Spring MVC | 对话 REST API、Thymeleaf 管理页和普通请求场景足够 |
| 数据访问 | Spring Data JPA | 数据模型关系清楚，CRUD 和分页实现成本低 |
| 数据库迁移 | Flyway | 启动时执行版本化 SQL，方便服务器持续升级 |
| 安全 | Spring Security | 管理员登录、Cookie 会话、接口授权和密码哈希 |
| 管理界面 | Thymeleaf + HTMX | 与 Spring Boot 打包成一个服务，避免维护第二套前端工程 |
| 健康检查 | Spring Boot Actuator | 为 Nginx、Docker 和发布脚本提供健康状态 |
| AI 扩展 | 自定义 `ChatProvider`，后续接 Spring AI 2.0 | 第一阶段不加载模型依赖，需要真实模型时再启用 |
| 构建 | Maven Wrapper | 构建版本固定，本机和服务器行为一致 |
| 部署 | 多阶段 Docker 镜像 + Compose | 服务器无需安装 Java 或 Maven，发布和回滚简单 |

## Provider 接口

```java
public interface ChatProvider {
    ChatResult reply(ChatContext context, String message);
    String name();
}
```

- `PresetChatProvider`：从 PostgreSQL 加载启用规则，完成关键词/正则评分和预制回答选择。
- `SpringAiProvider`：以后通过 Spring AI 的 `ChatClient` 调用真实模型。
- `RoutingChatProvider`：未来可先跑预制规则，低于置信度阈值时再转真实模型。

这种结构保证前端始终调用同一个 `/api/v1/chat`，切换模型不影响页面。

## 部署结构

```text
Nginx
  ├─ /              -> 静态网站目录
  ├─ /api/          -> 127.0.0.1:8080
  └─ /admin/        -> 127.0.0.1:8080

Docker: testproject-backend
  ├─ Spring Boot 4.1 / Java 21
  ├─ 仅监听 127.0.0.1:8080
  └─ 通过 host network 访问 127.0.0.1:5432 PostgreSQL
```

服务器当前为 4 核、7.4 GiB 内存、约 6.2 GiB 可用，运行一个限制在约 512 MiB 内存的 Spring Boot 后台没有压力。服务器本机没有 Java，因此使用 Docker 镜像提供完整运行时。

## 关键调整

| 决策点 | 选择 | 理由 |
|--------|------|------|
| Spring Boot 还是 FastAPI | Spring Boot | 用户明确偏好，长期后台、权限、数据管理和 AI 扩展更体系化 |
| Spring WebFlux 还是 MVC | MVC | 第一阶段均为短请求；无需为假模型提前引入响应式复杂度 |
| 是否立即引入 Spring AI | 不立即引入 | 先把 Provider 接口和预制模型做好，减少启动体积和无用配置 |
| JPA 还是 R2DBC | Spring Data JPA | 当前访问量与并发很小，事务和后台 CRUD 更直接 |
| 本机安装 Java还是 Docker | Docker | 不污染宝塔服务器系统环境，版本固定且方便回滚 |

## 调整后的实现计划

1. 使用 Spring Initializr 结构建立 Spring Boot 4.1 / Java 21 / Maven 后台。
2. 加入 Web、Validation、Data JPA、PostgreSQL Driver、Flyway、Security、Thymeleaf、Actuator。
3. 实现数据库迁移、预制数据、规则匹配器和 `PresetChatProvider`。
4. 实现 `/api/v1/chat`、会话记录、限流与测试。
5. 实现 `/admin` 登录、对话规则编辑和未命中问题管理。
6. Docker 化并接入 Nginx，再连接当前极简模式输入框。
7. 需要真实模型时，再加入 Spring AI 2.0 和 `SpringAiProvider`。
